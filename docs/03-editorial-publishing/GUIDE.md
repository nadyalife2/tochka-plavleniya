# Раздел 3: Подготовка и публикация статьи

Практическое руководство для авторов и редакторов портала «Точка Плавления».

> Актуально для темы `theme4.zip` (v4.0.0), плагина `tchp-content.zip` (v1.1.2) и Rank Math SEO. Изменения этого релиза: «не применимо» для припоя, чекбокс температур, автоподстановка по сплаву, пресеты стандартов (включая IPC-7093 и IPC-7095D), колонка GEO `N/6` со строгой валидацией FAQ (≥4) и источников (≥2), полный JSON-LD из паспорта статьи и контракт статьи v1.1.

В проекте строго разделены два сценария подготовки материалов:
* **Маршрут 1 (Ручная работа автора):** «Записи → Добавить новую» в WordPress, визуальный редактор Gutenberg, готовые инженерные паттерны, метабоксы плагина `tchp-content`, мобильный предпросмотр, проверка редактором и публикация. Автору **не требуется** вручную составлять JSON — стандартный веб-интерфейс обеспечивает полное оформление.
* **Маршрут 2 (Автоматизация / ИИ-пайплайн):** Бриф → генерация JSON-контракта → валидация по схеме `article-contract-v1.1.schema.json` (для старых контрактов 1.0 — `article-contract-v1.schema.json`) → консольная доставка черновика через `delivery_cli.py` → проверка шеф-редактором. JSON — это формат межпрограммного обмена, а не обязательный интерфейс живого автора.

## 1. Порядок ручной публикации автором (Маршрут 1)

Практическая последовательность действий автора в панели управления WordPress:
1. **Создать запись:** Открыть пункт меню `Записи → Добавить новую`.
2. **Выбрать формат:** Определить тип материала (инструкция, сравнение, справочник или диагностика).
3. **Вставить структуру и паттерны:** Сформулировать краткий прямой ответ в первом абзаце (паттерн `tochka-plavleniya/tldr-center`), добавить необходимые предупреждения (`tochka-plavleniya/safety-warning`), шаги процесса и таблицы.
4. **Заполнить «Паспорт статьи» (метабокс плагина `tchp-content`, v1.1.2):**
   * *Припой (`tchp_solder_alloy`):* канонический сплав из реестра **или «— не применимо —»**, если статья не про конкретный сплав (оборудование, химия, организация места, обзоры).
   * *Температуры:* сначала чекбокс **«Температурный режим применим к этой статье»**. Если он включён и выбран сплав, пустые поля диапазона/пика заполняются автоматически (SAC305 → 310–350 / 245 °C, ПОС-61 → 260–295 / 320 °C, Розе → 140–180 °C) — цифры можно и нужно править под задачу.
   * *Стандарт (`tchp_standard`):* выберите из подсказки (IPC-A-610G, J-STD-001, J-STD-020E, J-STD-004B, IPC-7093 для QFN/BTC, IPC-7095D для BGA, ГОСТ 21931-76, ГОСТ 21930-76, ANSI/ESD S20.20, IEC 61010-1) или впишите свой. Класс и пояснение — по необходимости.
   * *Инструменты (`tchp_tools`):* реальное оборудование (название, модель, назначение).
   * *FAQ (`tchp_faq_items`):* реальные практические вопросы и ответы (строго от 4 до 6 по стандарту v1.1).
   * *Источники (`tchp_sources`):* ГОСТ, IPC, технические даташиты (строго от 2 до 4 по стандарту v1.1).
   * После сохранения смотрите колонку **GEO `N/6`** в списке записей: припой, температуры, стандарт, источники, FAQ, ОТК.
5. **Проверить SEO в блоке Rank Math:** фокусное слово, сниппет, читаемость. **Schema в Rank Math вручную не заполняется** — JSON-LD собирается автоматически из паспорта статьи (см. §6).
6. **Предпросмотр:** Проверить адаптивное отображение в теме `theme4` (десктоп и мобильный вид).
7. **Редакционная проверка:** Нажать кнопку **«🛡️ Подтвердить проверку (ОТК)»** в метабоксе верификации (сохраняется через хук `save_post`, требует права `tchp_review_content`). Кнопка подтверждает текущую сохранённую редакцию; любая последующая правка текста или паспорта сбрасывает статус в `in_review`.
8. **Публикация:** Перевести запись в статус **Опубликовано** (`publish`).

## 2. Выбор формата и каталога паттернов

Перед оформлением статьи определите её инженерный тип:

| Тип материала | Задача | Ключевые структурные элементы |
|---|---|---|
| **Пошаговая инструкция (How-to)** | Обучить читателя конкретной операции монтажа/демонтажа | Паспорт режима, инструменты, пошаговые действия с контрольными точками |
| **Сравнительный анализ (Comparison)** | Помочь выбрать сплав, флюс или технологию под задачу | Сравнительная таблица параметров, физико-химические отличия, границы применимости |
| **Инженерный справочник (Reference)** | Дать точные справочные данные по стандарту (ГОСТ/IPC) | Таблицы ликвидус/солидус, допустимые температурные коридоры, ссылки на первоисточники |
| **Диагностика ошибок (Troubleshooting)** | Помочь найти причину дефекта пайки и исправить её | Паттерны «Симптом → Причина → Действие», фото/схемы «Норма vs Дефект» |

### Каталог контентных паттернов
Используйте инженерные паттерны осознанно. **Не нужно вставлять все паттерны в каждую статью подряд** — выбирайте только те, которые служат пониманию материала:

| Паттерн | Когда использовать | Пример оформления в HTML/Markdown (Gutenberg) |
|---|---|---|
| **Краткий ответ (TL;DR)** | В первом абзаце, сразу давая прямой содержательный ответ | Паттерн `tochka-plavleniya/tldr-center`:<br>`<p class="lead font-serif text-lg">[Пример формата, не норма: прямой ответ в 1–2 предложениях — что выбрать или сделать и при каких условиях.]</p>` |
| **Предупреждение (Warning)** | Когда есть риск термоудара компонента, отрыва дорожки или вреда здоровью | Паттерн `tochka-plavleniya/safety-warning`:<br>`<div class="note-box alert-warning"><strong>Внимание:</strong> [Проверенное предупреждение с указанием граничных условий, режима и источника]</div>` |
| **Инструменты и оснастка** | Для фиксации только реально необходимых приборов | Паттерн `tochka-plavleniya/tools-needed` или метаполе `tchp_tools` (название, модель, назначение) |
| **Последовательные шаги** | Для описания технологического процесса | `<ol class="steps-list"><li>Шаг 1: Очистка полигона...</li><li>Шаг 2: Нанесение флюса...</li></ol>` |
| **Сравнительная таблица** | Для сопоставления численных характеристик | `<table><thead><tr><th>Сплав</th><th>T плавления</th><th>Прочность</th></tr></thead>...</table>` |
| **Симптом → Причина → Действие** | Для разбора брака пайки (галтели, каверны, шарики) | **Симптом:** Матовая зернистая поверхность.<br>**Причина:** Движение детали в интервале кристаллизации.<br>**Решение:** Зафиксировать пинцетом до полного застывания. |
| **Норма vs Дефект** | Для наглядного объяснения критериев IPC-A-610 | Описание или векторная схема идеальной вогнутой галтели против избыточного шарообразного наплыва |
| **Вопросы и ответы (FAQ)** | Для ответа на реальные практические вопросы читателя | Заполняется в метаполе `tchp_faq_items` (массив `{"q": "...", "a": "..."}`) |
| **Источники и стандарты** | Для доказательной базы приведенных чисел и режимов | Заполняется в метаполе `tchp_sources` (ГОСТ, IPC, JEDEC) |
| **Секция: где ошибаются** | Цена типичной ошибки | Паттерн `tochka-plavleniya/section-mistakes` |
| **Секция: признаки результата** | Проверка после каждого шага | Паттерн `tochka-plavleniya/section-result-signs` |
| **Секция: нюансы** | Ситуации, которых новичок не ждёт | Паттерн `tochka-plavleniya/section-nuances` |
| **Секция: диагностика** | Симптом → причина → решение | Паттерн `tochka-plavleniya/section-diagnostics` |
| **Секция: сравнение** | Варианты по понятным параметрам | Паттерн `tochka-plavleniya/section-comparison` |
| **Секция: если не получилось** | Безопасный откат и повтор | Паттерн `tochka-plavleniya/section-if-failed` |

### Расширение статьи: разделы, а не абзацы

Ориентир по объёму — **5 500–7 000 знаков**. Готовые тексты в листе `statiy` дают
5 820–9 031 знак; черновики 2 500–4 100 знаков. Значит, каждой нужно добавить
2 000–3 000 знаков **новыми смысловыми блоками**, а не «водой».

Стиль ориентирует на короткие предложения (до 18 слов) и плотные абзацы в 1–3 предложения
([`MASTER_EDITORIAL_BOOK.md`](../../gem-knowledge/MASTER_EDITORIAL_BOOK.md), глава 2). Поэтому объём растёт
разделами, таблицами и проверками.

| Блок | Прирост | Что писать |
|---|---:|---|
| Где ошибаются и почему это важно | 500–700 | типичное заблуждение и цена ошибки |
| Признаки результата в каждом шаге | 400–600 | что видно, слышно или измеримо после шага |
| Нюансы | 500–800 | 2–4 ситуации, которых новичок не ждёт |
| Диагностика «симптом → причина → решение» | 400–700 | таблица на 4–6 строк |
| Сравнение или таблица | 300–500 | варианты по понятным параметрам |
| FAQ | 400–600 | 5–6 реальных вопросов, ответы по 1–3 предложения |
| Что делать, если не получилось | 300–500 | короткий откат и повторная попытка |

Новые паттерны темы: `section-mistakes`, `section-result-signs`, `section-nuances`,
`section-diagnostics`, `section-comparison`, `section-if-failed`.

**Порядок:** проблема → признаки результата → нюансы → диагностика → сравнение →
FAQ → что делать, если не получилось. Берите 3–4 блока, пока не дойдёте до цели.

**Проверка пользы:** блок остаётся, если даёт действие, признак результата,
различие, ограничение или ответ на реальный вопрос. Если без него статья ничего
не теряет — не пишем.

**По группам:**
- основы: упражнение на обрезках, «хороший шов против плохого», время контакта;
- инструмент: «я паяю X — нужен Y», «больше ватт — лучше?», износ жал;
- флюсы: «задача → тип флюса → отмывка», дозирование, остатки;
- безопасность: чек-лист места, вытяжка по бюджету, медицинские советы — только по надёжным источникам;
- ошибки: диагностика с фото-описанием, порядок проверок, перелинковка;
- припои: таблица сплавов, маркировка катушки, совместимость с флюсом, переход.

**Нельзя:** выдумывать время, диаметры и уставки; повторять краткий ответ;
писать вывод-пересказ; шутить в разделах про безопасность.

**Запрещённые слова** — проверить поиском:
```bash
grep -nE 'необходимо|следует|осуществляется|выполните|важно отметить' <файл>
```

**Рабочая схема:**
1. Перечитать статью: на что читатель не получил ответа?
2. Выбрать 3–4 блока из таблицы.
3. Дописать по главе 2 редакционной книги: короткие понятные предложения и компактные абзацы. 18 слов — ориентир читаемости, а не жёсткий предел; не искажать технические условия ради лимита.
4. Прогнать самопроверку стиля.
5. Проверить новые цифры по источникам.
6. После этого — перелинковка по `interlinking_map`.

> В ручном Маршруте 1 таких ограничений нет: припой — «— не применимо —», температуры — снятый чекбокс.

### JSON для нейросетей: что должно быть внутри

JSON — не сокращённый пересказ, а полный контракт статьи для генератора и доставки.

| Поле | Что содержит | Требование |
|---|---|---|
| `content_html` | полный HTML: H2/H3, таблицы, шаги, FAQ | не краткое резюме; блоки соответствуют видимому тексту |
| `faq` | 4–6 пар `{q, a}` | совпадают с видимым FAQ; строго $\ge 4$ вопросов |
| `sources` | 2–4 `{title, standard, url}` | реальные ГОСТ/IPC/даташиты; строго $\ge 2$ источников, без `[web:*]` |
| `temp_data` | тип, диапазон, пик | только проверенные цифры |
| `standard_data` | стандарт, класс, пояснение | по паспорту статьи |
| `tools` | название, модель, назначение | только реальное оборудование |
| `excerpt` | прямой ответ на запрос | без кликбейта |

Схема **v1.1** строго валидирует обязательное наличие `faq` (4–6) и `sources` (2–4), а также расширенный набор категорий (`materialy`, `praktika`, `oshibki`, `start-i-baza`, `baza-znanij`, `oborudovanie`). Схема v1 сохраняется для обратной совместимости.

## 4. Доставка черновика в WordPress

Отправка статьи выполняется через защищённый консольный инструмент [`tools/delivery_cli.py`](../../tools/delivery_cli.py):

```bash
python tools/delivery_cli.py send-draft \
  --file article.json \
  --wp-url "https://tochka-plavleniya.ru" \
  --wp-user "automation_bot" \
  --wp-pass "xxxx xxxx xxxx xxxx"
```

### Что происходит при доставке:
1. **Валидация:** Файл проверяется по схеме, соответствующей `schema_version` (1.1 или 1.0).
2. **Разрешение терминов:** Скрипт сопоставляет `category_slug` и `tags` с реальными ID таксономий в WordPress.
3. **Защита данных:** Если статья уже опубликована или в неё вносились ручные правки редактора — доставка блокируется с конфликтом (код выхода `3`).
4. **Фиксация в журнале:** В `delivery-journal.json` фиксируется состояние `sending`, а затем результат с полученным ID поста.
5. **Read-after-Write:** Скрипт перечитывает созданную запись из WordPress и выполняет глубокую сверку всех сохранённых метаполей. При несовпадении возвращается код ошибки `4`.

## 5. Редакционная вычитка и подтверждение верификации

После доставки черновика процесс переходит к человеку — шеф-редактору:

### Разделение статусов WordPress и редакции:
* **Статус записи WordPress (`post_status`):** стандартные системные состояния платформы — `draft` (черновик), `pending` (на утверждении) или `publish` (опубликовано). Доставка создает записи исключительно в статусе `draft` или `pending`.
* **Редакционный статус качества (`tchp_review_status`):** внутренний статус плагина `tchp-content` — `unreviewed` (не проверено), `in_review` (на проверке) или `verified` (верифицировано). При любой доставке или повторном сохранении текста плагин выставляет статус не выше `in_review`.

### Порядок работы редактора:
1. Редактор открывает черновик в панели управления WordPress (`/wp-admin/post.php?post=ID&action=edit`).
2. Проверяет корректность текста, терминов, температурных параметров и мобильное отображение через предварительный просмотр темы `theme4`.
3. **Подтверждение в административной панели:** В метабоксе верификации редактор нажимает кнопку **«Подтвердить редакцию»**. Подтверждение сохраняется при стандартной отправке формы редактирования записи через хук `save_post` (требует право `tchp_review_content`). Плагин вычисляет контрольный хеш контента и метаполей, фиксирует ID ревьюера (`tchp_reviewer_id`), дату и переводит редакционный статус в `verified`.
4. **Программная верификация через REST API:** Для внешних сервисов и скриптов доступен отдельный эндпоинт `POST /wp-json/tchp/v1/posts/{id}/verify`. Он требует права `tchp_review_content` и обязательный параметр `expected_hash`:
   * Если статья за время передачи изменилась — сервер возвращает **409 Conflict**.
   * Если хеш совпал — сервер возвращает **200 OK** и присваивает статус `verified`.
5. Редактор принимает решение о публикации и переводит статус записи WordPress в **Опубликовано** (`publish`).

### Редактирование уже опубликованной статьи:
Если в проверенную статью вносятся любые текстовые изменения — плагин `tchp-content` через хук `wp_after_insert_post` **автоматически сбрасывает статус** в `in_review` (`tchp_review_outdated = 1`). Это защищает сайт от расхождения между знаком качества и изменённым текстом.

## 6. SEO и GEO в контексте статьи

Для правильной индексации и ранжирования автором заполняются стандартные поля без необходимости вручную писать код JSON-LD или придумывать искусственные гео-теги.

> **GEO в этом документе** — Generative Engine Optimization (оптимизация под ИИ-поиск: ChatGPT, Perplexity, Яндекс Нейро, AI Overviews), а не география. Гео-привязки к городам в инженерных статьях запрещены (см. принципы ниже).

### Таблица соответствия полей:
| Поле | Где заполнять | Для чего используется |
|---|---|---|
| **Заголовок (Title)** | Поле заголовка записи / сниппет Rank Math | Формирует тег `<title>`, тег `<h1>` и сниппет в поисковой выдаче |
| **Краткий отрывок (Excerpt)** | Метабокс «Отрывок» / Rank Math Description | Мета-тег `description`, карточки в рубриках и сниппет поиска |
| **Первый абзац (TL;DR)** | Первый блок Gutenberg (паттерн `tldr-center`) | Прямой ответ на запрос читателя для людей и поисковых AI-систем (AI Overviews) |
| **Рубрика (Category)** | Боковая панель WordPress «Рубрики» | Архитектура сайта, URL статьи и хлебные крошки `BreadcrumbList` |
| **Метки (Tags)** | Боковая панель WordPress «Метки» | Навигация по сходным терминам/сплавам (гео-спам строго запрещён) |
| **Припой (`tchp_solder_alloy`)** | Метабокс «Паспорт статьи» | `additionalProperty` (PropertyValue) и `keywords`; при «— не применимо —» не выводится |
| **Температуры (`tchp_temp_kind`, `tchp_temp_range`, `tchp_temp_peak`)** | Метабокс «Паспорт статьи» | `additionalProperty`: тип, диапазон, пик. Выводятся только если заполнены |
| **Стандарт (`tchp_standard`, `tchp_standard_class`, `tchp_standard_description`)** | Метабокс «Паспорт статьи» | `additionalProperty` + `isBasedOn` |
| **ОТК (`tchp_review_status`, `tchp_reviewer_id`, `tchp_reviewed_at`)** | Метабокс «Редакционная проверка (ОТК)» | `reviewedBy` и дата проверки — сигнал E-E-A-T для людей и ИИ |
| **FAQ (`tchp_faq_items`)** | Метабокс плагина `tchp-content` | Визуальный блок вопросов/ответов + Schema.org `FAQPage` (выводится автоматически) |
| **Источники (`tchp_sources`)** | Метабокс плагина `tchp-content` | Блок доказательной базы статьи + `citation` в JSON-LD |

### Заполнение паспорта по типу статьи

| Тип статьи | Припой | Температуры | Стандарт |
|---|---|---|---|
| Сплавы, пайка, BGA/SMD, термопрофили | конкретный (ПОС-61, SAC305…) | да, чекбокс включён | IPC-A-610G, ГОСТ 21931-76 |
| Дефекты и брак | конкретный или «не применимо» | если разбирается режим/перегрев | IPC-A-610G |
| Оборудование (станции, фены, жала, микроскопы) | «— не применимо —» | как правило нет | можно пусто или профильный (IEC 61010-1) |
| Химия (флюсы, отмывка, пасты) | «— не применимо —» | если про режимы | J-STD-004B |
| Организация места, ESD, безопасность | «— не применимо —» | нет | ANSI/ESD S20.20 |
| Обзор/сравнение («T12 vs C245») | «— не применимо —» | по желанию | можно пусто |

**Всегда заполняются:** сложность, инструменты, FAQ, источники, ОТК — это универсальный GEO-каркас.

### Что попадает в JSON-LD

Один раз заполнили паспорт — данные идут в статью (визуальные блоки), в JSON-LD и в REST:

* `TechArticle`: заголовок, описание, даты публикации/изменения, автор, издатель, `inLanguage`, `proficiencyLevel`, `wordCount`, `articleSection`, `keywords`;
* `additionalProperty`: припой, тип/диапазон/пик температуры, стандарт, класс, пояснение;
* `citation`: источники; `reviewedBy`: ОТК; `FAQPage`: FAQ; `BreadcrumbList`: хлебные крошки;
* пустые и неприменимые поля **не выводятся** — схема остаётся валидной.

**Два режима работы (менять вручную ничего не нужно):**
* у Rank Math включён модуль rich-snippet (по умолчанию) — Rank Math печатает `Article`, а факты из паспорта подмешиваются в его JSON-LD фильтром `rank_math/json_ld`;
* модуль выключен — полную схему печатает тема (`TechArticle` + `BreadcrumbList` + `FAQPage`).

Дублировать припой/температуры во вкладке Schema Rank Math не нужно.

### Чек-лист перед публикацией

1. Заголовок и TL;DR в первом абзаце — прямой ответ на запрос.
2. Припой выбран из реестра **или** осознанно «— не применимо —».
3. Если температуры применимы — чекбокс включён, диапазон и пик проверены (автоподстановка — только стартовый ориентир).
4. Стандарт указан (или осознанно оставлен пустым для тем без норматива).
5. Инструменты, **4–6 FAQ**, **2–4 источника** заполнены.
6. Рубрика и метки проставлены.
7. Объём **5 500–7 000 знаков**; есть 3–4 блока расширения (ошибки, признаки, диагностика, откат).
8. Проверены канцелярит, пустые связки и читаемость по главе 2 редакционной книги. Предложения и абзацы компактные; технически необходимые термины и условия сохранены. Формальное превышение 18 слов само по себе не является ошибкой.
9. Если FAQ есть и в тексте, и в `tchp_faq_items`, они совпадают по смыслу; в предпросмотре убедиться, что блок не выводится дважды.
10. Внутренние ссылки из `interlinking_map` стоят в естественных местах.
11. Колонка **GEO `N/6`** в списке записей: 6/6 — полный паспорт; 4–5/6 — норма для не-паяльных тем.
12. **«🛡️ Подтвердить проверку (ОТК)»** — последним действием, после всех правок текста.

Проверка разметки после публикации: Rich Results Test / Schema Markup Validator по URL статьи; в исходном коде страницы — один блок JSON-LD с `TechArticle` (или `Article` от Rank Math) и `additionalProperty`.

### Принципы доказательного SEO и GEO:
* **Прямой ответ (Answer First):** Поисковые системы и AI-агенты извлекают ответ из первого абзаца статьи. Не начинайте статью со слов «Введение» или пространных рассуждений.
* **Канонический Schema-граф:** разметка собирается автоматически из паспорта статьи — тема отдаёт `TechArticle`/`Article`, `BreadcrumbList`, `FAQPage`, `additionalProperty` и `citation`. Если разметкой владеет Rank Math (модуль rich-snippet), факты из `tchp_*` полей подмешиваются в его узел через `rank_math/json_ld`; вручную дублировать Schema не нужно.
* **Неприменимые поля:** статья про оборудование, химию или организацию места не обязана иметь припой и температуры — выберите «— не применимо —» и снимите чекбокс температурного режима. Пустые поля не попадают в JSON-LD.
* **Экстерриториальность:** Инженерные статьи носят экстерриториальный характер — в них запрещено вставлять фиктивные гео-привязки («пайка плат в городе N»). Города указываются только для реальных физических мастерских или филиалов.
* **Ограничения GEO:** Документация Google Developers подтверждает: файл `llms.txt` не является обязательным для AI-функций Google и не гарантирует попадание в ответы. Главные критерии — фактическая точность, проверяемые источники, прозрачные даты публикации и высокая скорость загрузки.
