# Генеральный сквозной конвейер «Точка Плавления» (Master Pipeline)

Документ описывает сквозную цепочку: от темы до черновика WordPress, редакционной проверки, автоматического тестирования и безопасной доставки. Автоматическая публикация строго запрещена.

---

## Статус реализации

| Блок | Статус |
|---|---|
| JSON-контракт статьи | Реализован в `schemas/article-contract-v1.schema.json` |
| Валидация REST-метаполей | Реализована в `tchp-content` (с защитой от пустых HTML-тегов) |
| Каноническая уникализация якорей | Реализована в `theme4/includes/functions.php` (`tchp_process_article_anchors`) |
| Отпечаток статьи и `expected_hash` | Реализованы в `tchp-content` |
| Генератор статей через Gemini | Реализован в `tools/ai_article_generator.py` (голос Practico, черновик) |
| Безопасная доставка в WordPress (Пакет Б) | Реализована в `tools/delivery_cli.py` (draft-only, защита от перезаписи, журнал, read-back) |
| Интеграционные тесты на живом WP | Реализованы в `tools/test_live_wp_integration.py` (требует реальный WordPress) |
| Автоматическое самообучение Build Partner | Спецификация и скрипты созданы; фоновая автоматизация запускается по запросу |

---

## Целевая сквозная цепочка

```text
Тема и SEO/GEO-ТЗ
→ исследование и проверка фактов (solder-researcher)
→ статья в голосе Practico (solder-writer)
→ редакторская и техническая вычитка (solder-reviewer)
→ структурирование сниппетов (solder-seo-planner)
→ нормализация и валидация JSON по article-contract-v1.schema.json
→ безопасная доставка в WordPress как draft/pending (delivery_cli.py)
→ вычитка шеф-редактором в WP-admin
→ подтверждение expected_hash (POST /wp-json/tchp/v1/posts/{id}/verify)
→ ручное решение о публикации в WordPress
```

## Контракт статьи

Источник истины — `schemas/article-contract-v1.schema.json`.

Обязательные поля:
- `content_id` (формат: `^tchp-[a-z0-9-]+$`)
- `schema_version` (строго `"1.0"`)
- `title`
- `slug`
- `excerpt`
- `category_slug` (`start`, `materialy`, `praktika`, `oshibki`)
- `tags`
- `reading_time` (целое число от 1 до 60)
- `difficulty` (`Базовый`, `Инженер`, `Эксперт`)
- `solder_alloy` (канонический ID)
- `temp_data` (объект `kind`, `range`, опционально `peak`)
- `tools` (массив объектов `name`, `model`, `purpose`)
- `content_html`

Дополнительные поля:
- `content_hash`
- `faq` (массив объектов `q`, `a`)
- `sources` (массив объектов `title`, `standard`, `url`)
- `standard_data` (объект `standard`, `class`, `description`)

### Разрешённые идентификаторы сплавов:
```text
pos61, sn63pb37, pos40, sac305, sac405,
sn42bi58, snbiago, roze, vuda, universal
```

Алиасы нормализуются до валидации:
```text
wood -> vuda
rose -> roze
```

## Голос автора

Статьи пишутся в голосе Practico:
- Читатель — новичок по знаниям, но коллега по достоинству.
- Формула абзаца: термин → механизм одной фразой → наблюдение или последствие.
- Наблюдаемые признаки процесса обязательны там, где они уместны: цвет, блеск, текучесть, дым, звук, время.
- Ошибки разбираются по схеме: симптом → причина → решение.

Категорически запрещено:
- выдумывать личный опыт или несуществующие кейсы из мастерской;
- имитировать измерения, приборы или фотографии;
- использовать бытовые и кулинарные метафоры;
- давать обещания результата без физического механизма;
- подменять технический факт стилем.

При любом конфликте стиля и физического факта приоритет всегда у факта.

## Презентация и Вёрстка (theme4 Frontend)

1. **Рендеринг статьи (`single.php`):**
   - Вывод технического паспорта с интерактивной плашкой температуры и сплава.
   - Вывод структурированных инструментов, источников и аккордеона FAQ из метаполей.
2. **Каноническая уникализация DOM-якорей документа (`tchp_process_article_anchors`):**
   - Функция в `theme4/includes/functions.php` нормализует все ID элементов документа (включая не-H2 теги `div`, `section`), сканирует заголовки H2-H4, генерирует транслитерированные якоря и гарантирует 100% уникальность ID в DOM без коллизий.
3. **SEO-делегирование и Адаптив:**
   - Тема проверяет модуль Rank Math Rich Snippet и уступает генерацию Schema.org плагину SEO при его наличии.
   - Вёрстка в стиле Bento-Sketch Hybrid (бумажный фон, карандашный контур 1px, монохромный вектор SVG) протестирована на экранах **375px**, **768px**, **1024px** и **1440px**.

## Безопасная доставка в WordPress (Пакет Б)

Инструмент доставки: `tools/delivery_cli.py`.

### Ключевые инварианты безопасности:
1. **Только черновик:** Допустимы исключительно статусы `draft` и `pending`. Статус `publish` запрещён.
2. **Защита опубликованных записей:** Ни при каких условиях не перезаписывает опубликованные статьи.
3. **Разрешение таксономий:** Автоматически сопоставляет `category_slug` и `tags` с реальными ID терминов в WordPress.
4. **Контроль ручных правок:** Если статья уже была проверена редактором (`tchp_review_status == 'verified'`) или её отпечаток изменился относительно журнала — обновление отклоняется с конфликтом.
5. **Атомарный журнал доставок:** Ведётся в `delivery-journal.json` с разделением по целевым сайтам (`site_url`) и внешнему `content_id`. Защищён файловой блокировкой и атомарной записью. Статус `sending` фиксируется до запроса, при обрыве связи выставляется `outcome_unknown`.
6. **Полноценный Read-Back:** После записи выполняется контрольный GET-запрос с побайтовой сверкой всех сохранённых метаполей с отправленным JSON. При несовпадении статус помечается как `unconfirmed`, а CLI возвращает ненулевой код выхода.

## WordPress и Редакционная Верификация

Плагин `tchp-content` отвечает за:
- Регистрацию инженерных метаполей и схем в WP REST API.
- Серверную валидацию (включая запрет пустых строк после очистки HTML-тегов).
- Защиту от затирания существующих полей при частичных обновлениях (`rest_pre_insert_post`).
- Расчёт SHA-256 отпечатка содержимого статьи (`tchp_calculate_article_hash()`).
- Экспертное подтверждение редакции через `POST /wp-json/tchp/v1/posts/{id}/verify` с параметром `expected_hash` (возвращает `409 Conflict` при несовпадении).
- Автоматический сброс статуса верификации в `in_review` (`outdated = 1`) при любом последующем изменении проверенного контента.

## GEO и Разметка

GEO основан на понятной структуре страницы:
- Прямой ответ на технический вопрос в начале раздела.
- Самодостаточные, цитируемые разделы.
- Проверяемые факты, ссылки на стандарты и корректные даты.
- FAQ создаётся только при наличии реальных вопросов аудитории.

`llms.txt` не является гарантией индексации в AI-поиске. Документация Google подтверждает, что для попадания в AI-функции поиска не требуется специальный `llms.txt` или отдельная искусственная разметка. Разметка JSON-LD должна строго соответствовать видимому содержимому страницы.

## Тестирование и Сборка

1. **Локальный раннер `tests/run-all-tests.py`:**
   - Валидация JSON Schema Draft-07 и соответствия примера контракту.
   - Синтаксический анализ (php -l) всех модулей плагина и темы.
   - Набор тестов бизнес-логики и контрактов REST (Mock WP, 38 assertions).
   - Пофайловая сверка состава и побайтовое соответствие ZIP-архивов исходным файлам.
   - Разделение на верификацию существующего архива (`--verify-only`) и сборку нового (`--build`).

2. **Интеграционное тестирование на живом WordPress (`tools/test_live_wp_integration.py`):**
   - Запускается на реальном стенде WordPress с базой данных MySQL.
   - Проверяет аутентификацию по Application Password, создание черновика, валидацию пустых HTML-тегов, частичные обновления, права редактора vs автора автоматизации и блокировку устаревшего `expected_hash` (строго HTTP 409).
   - Выполняет обязательную очистку тестовых записей.

3. **GitHub Actions CI (`.github/workflows/ci.yml`):**
   - Запускает тесты на чистом окружении Ubuntu (PHP 8.2 + Python 3.12).
   - Валидирует код, контракты и собирает релизные архивы в артефакты сборки.
   - *Примечание:* CI не разворачивает WordPress с базой данных, поэтому подтверждает целостность кода, но не заменяет прогон на живом WordPress.

## Самообучение (`build-partner`)

Скилл `build-partner` (`Improve System`) анализирует подтверждённые замечания, историю ревью и формулирует уточнения для стандартов репозитория.

Правило фиксируется в репозитории только при выполнении условий:
- Указан первоисточник и контекст замечания.
- Проверена актуальность и отсутствие противоречий с базовыми инженерными требованиями.
- Получено явное подтверждение пользователя.
