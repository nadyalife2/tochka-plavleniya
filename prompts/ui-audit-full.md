ЭТАП 1 — Изучение
Изучи материалы. Не меняй код, не создавай файлы, не предлагай итоговую
вёрстку до завершения аудита и моего подтверждения направления.

ЭТАП 2 — Оценка по 16 критериям

1. ПОНИМАНИЕ ЗА 5 СЕКУНД
   — Ясно ли, что это за сайт и для кого?
   — Есть ли ценностное предложение в первом экране?
   — Совпадают ли ожидания аудитории с тем, что они видят?

2. HERO И ПЕРВЫЙ ЭКРАН
   — Заголовок: конкретный или расплывчатый?
   — CTA: есть ли, куда ведёт, насколько заметен?
   — Визуальный фокус: куда смотрит глаз в первые 2 секунды?
   — Скетч-элементы / иллюстрации hero: работают или мешают?

3. ВИЗУАЛЬНАЯ ИЕРАРХИЯ
   — Порядок восприятия: H1 → подзаголовок → карточки → CTA.
   — Что конкурирует за внимание одновременно?
   — Правило трёх уровней: заголовок / контент / служебное.

4. СЕТКА И РИТМ
   — Контейнер: правильная ширина для чтения (max 1160 px)?
   — Вертикальный ритм: кратность 8 pt?
   — Плотность: где слишком тесно, где слишком пусто?
   — Выравнивания: есть ли случайные отступы?

5. ТИПОГРАФИКА
   — Размеры: H1, H2, body, caption, meta, code — различимы ли?
   — Длина строки: 60–75 символов для чтения тела?
   — Межстрочный интервал body: 1.6–1.75?
   — Монospace: где уместен IBM Plex Mono, где он перегружает?
   — Жирность и курсив: используются осмысленно или декоративно?

6. КАРТОЧКИ СТАТЕЙ
   — Сканируемость: можно ли понять тему за 1–2 секунды?
   — Обязательные элементы: рубрика / заголовок / дата / время чтения.
   — Изображение: есть ли, нужно ли, как обрезается на mobile?
   — Hover: ясен ли сигнал кликабельности?
   — Плотность ленты: не слишком ли похожи все карточки?

7. НАВИГАЦИЯ
   — Разделы: логичны ли для аудитории?
   — Поиск: есть ли, заметен ли?
   — Mobile-меню: гамбургер или что-то лучше?
   — Активные состояния: видно ли, где ты находишься?
   — Sticky header: помогает или мешает на мобильном?

8. СТРАНИЦА СТАТЬИ (оцени по коду или скриншоту если есть)
   — TL;DR-блок: есть ли, на каком месте?
   — Оглавление: sticky или нет, на каком устройстве пропадает?
   — Код: подсветка синтаксиса, кнопка копирования, горизонтальный скролл?
   — Callout-блоки: tip, warning, info — есть ли, различимы ли?
   — Иллюстрации: подписи, alt-текст, lazy-load?
   — Related posts: есть ли, насколько релевантны по алгоритму?
   — CTA после чтения: что предлагается сделать дальше?

9. ДОВЕРИЕ И АВТОРСТВО
   — Видно ли, кто написал и когда?
   — Есть ли пометка «обновлено»?
   — Есть ли пояснение, где контент создан с AI?
   — Видна ли экспертиза автора без биографической страницы?

10. ДОСТУПНОСТЬ (WCAG AA)
    — Контраст текста: проверь пары bg-paper/text-main и accent/white.
    — Focus states: видимы ли при keyboard-навигации?
    — Тап-зоны: минимум 44×44 px на mobile?
    — Alt-тексты: есть ли у всех изображений?
    — Reduced motion: есть ли @media (prefers-reduced-motion)?
    — Семантика: правильные теги article, nav, main, aside?

11. АДАПТИВНОСТЬ
    — Desktop 1440: сетка, контейнер, типографика.
    — Tablet 768: переход сетки, меню, карточки.
    — Mobile 390: тап-зоны, hero, навигация, чтение статьи.
    — Конкретно: что ломается или сжимается некрасиво?

12. ПРОИЗВОДИТЕЛЬНОСТЬ (визуальные риски)
    — backdrop-filter: сколько слоёв, есть ли GPU-нагрузка?
    — Анимации: transition duration > 300ms — замедляют восприятие?
    — Шрифты: preload, font-display: swap, сколько начертаний?
    — CLS-риски: зарезервированы ли размеры под изображения?
    — SVG-эффекты (feTurbulence): влияют ли на fps при скролле?

13. SEO-СИГНАЛЫ В ВЁРСТКЕ
    — Один H1 на странице?
    — Структура заголовков: H1 → H2 → H3 без пропусков?
    — Open Graph и meta description — есть ли заглушки в шаблоне?
    — Schema.org Article — подготовлена ли разметка?
    — Canonical и hreflang — нужны ли для русскоязычного блога?

14. САМОБЫТНОСТЬ И ХАРАКТЕР
    — Что уже создаёт уникальный характер «Точки Плавления»?
    — Что выглядит шаблонно, скопированно или безлико?
    — Sketch-элементы: работают как бренд или как декор ради декора?
    — Оранжевый акцент: правильно ли дозирован или везде одинаково?

15. КОНКУРЕНТНАЯ ПОЗИЦИЯ
    — Чем этот сайт визуально отличается от Habr, VC.ru, Точки над ИИ?
    — Есть ли хотя бы одна деталь, которую посетитель запомнит?
    — Что нужно добавить, чтобы сайт выглядел «своим», а не клоном?

16. ТРЕНДЫ (только если улучшают, не ради тренда)
    — Editorial-типографика: крупные засечки для акцентов?
    — Текстурный фон: зернистость/шум как часть бренда?
    — Inline-аннотации и сноски вместо длинных блоков?
    — Прогресс-бар чтения на странице статьи?
    — Dark mode: нужен ли для технической аудитории?

C. ТАБЛИЦА ПРОБЛЕМ
   | Приоритет | Блок / экран | Проблема (факт) | Почему критично | Точная правка |
   |-----------|--------------|-----------------|-----------------|---------------|

   Приоритеты:
   P0 — мешает пониманию, чтению или конверсии. Исправить до публикации.
   P1 — заметно улучшит качество. Исправить в первой итерации.
   P2 — полировка, детали. Можно отложить.

   Минимум: 3 проблемы P0, 5 проблем P1, любое количество P2.

D. ЧТО ОСТАВИТЬ ОБЯЗАТЕЛЬНО
   Назови 5–10 конкретных решений, которые уже работают и нельзя потерять.
   Для каждого — одно предложение: почему это ценно.

E. ТРИ НАПРАВЛЕНИЯ УЛУЧШЕНИЯ

   Для каждого направления дай:
   — Название и одну фразу-характеристику.
   — Что меняется (список конкретных элементов).
   — Что остаётся без изменений.
   — Какие UI-паттерны использовать (с названиями).
   — Риски реализации в WordPress + ACF.
   — Почему это направление подходит аудитории.
   — Примерная трудоёмкость (часы/дни).

   1. КОНСЕРВАТИВНОЕ
      Улучшает текущую идею без редизайна.
      Цель: убрать P0-проблемы, улучшить читаемость и доверие.

   2. СБАЛАНСИРОВАННОЕ
      Лучшее соотношение самобытности, читабельности и трудозатрат.
      Цель: сайт выглядит готовым продуктом, а не прототипом.

   3. СМЕЛОЕ
      Заметный editorial-редизайн, который запоминается.
      Цель: сайт становится визуально самостоятельным медиа.
      Ограничение: не перегрузить, не сломать PHP-архитектуру.

F. РЕКОМЕНДОВАННОЕ НАПРАВЛЕНИЕ
   Выбери одно из трёх. Аргументируй с учётом:
   — текущего состояния наброска;
   — технических ограничений WordPress;
   — аудитории (технари, читают с ноутбука и телефона);
   — реального времени на внедрение.

G. ОБНОВЛЁННЫЕ DESIGN TOKENS
   Предложи полный набор в формате CSS Custom Properties:

   Цвета:
   — фон, текст, акцент, secondary accent, muted, borders, overlay.
   — отдельно: состояния success/warning/error для callout-блоков.

   Типографика:
   — font-family для заголовков, тела, моно.
   — размеры: xs / sm / base / lg / xl / 2xl / 3xl / 4xl.
   — line-height и letter-spacing для каждого уровня.
   — максимальная ширина строки для чтения (ch).

   Spacing (8-pt scale):
   — 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 96 / 128 px.

   Радиусы:
   — sm / md / lg / pill / circle.

   Тени:
   — card / elevated / sticky-header / modal.

   Границы:
   — default / accent / muted.

   Состояния:
   — hover: transform или opacity, duration.
   — focus: outline, offset, color.
   — active: scale или brightness.
   — disabled: opacity.

   Анимации:
   — duration-fast / duration-normal / duration-slow.
   — easing: ease-out для появления, ease-in-out для переходов.
   — правило: анимация должна длиться ≤ 250ms для интерактивных элементов.
   — правило для @media (prefers-reduced-motion): отключить transform/opacity.

   Sketch-элементы:
   — когда использовать SVG-штрихи, где нет.
   — правило дозирования зернистости (opacity, placement).
   — правило для иллюстраций: только stroke, без fill, толщина 1.5–2 px.

H. ПЛАН ВНЕДРЕНИЯ

   Этап 1 — Быстрые правки (до 1 рабочего дня)
   Список конкретных файлов и изменений. Только P0.

   Этап 2 — Важные правки (2–4 дня)
   Список с приоритетом P1. Порядок выполнения важен.

   Этап 3 — Визуальная полировка (опционально)
   P2 и улучшения характера бренда. Можно делать после запуска.

   Для каждого этапа: файл → что менять → ожидаемый результат.

## Как использовать

1. Замени `[ВСТАВИТЬ URL ИЛИ ПУТЬ]` на реальную ссылку или путь к файлу.
2. Если есть Playwright MCP — агент сам откроет страницу и сделает скриншоты.
3. Если только код — вставь HTML прямо в чат перед промптом.
4. После получения отчёта используй **[ui-audit-after.md](./ui-audit-after.md)** для ТЗ.
5. Для аудита отдельных блоков — **[ui-audit-block.md](./ui-audit-block.md)**.
